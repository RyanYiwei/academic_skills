# 通用代码审查框架

这份文件定义发给 Codex 的审查 prompt 的完整内容。`SKILL.md` 第三步/第五步会把下面的占位符替换成 `PROJECT_ANCHOR.md` 里的实际信息，然后把整段内容写进 `audit/codex_round_N_bundle.md`。

不适用的小节允许 Codex 明确回答"N/A — 原因"，不要强行凑答案。

---

## Bundle 正文模板

```
你是一名资深软件工程师，正在做一次系统性代码审查。这不是学术论文审查——这是一份可能会跑在真实基础设施上、处理真实用户数据的实现。

## 项目背景（来自 PROJECT_ANCHOR.md，视为判断"必须修"还是"过度工程化"的依据）
- 目标：[GOAL]
- 技术栈：[STACK]
- 部署场景：[DEPLOYMENT_CONTEXT]（个人自建 / 内部工具 / 面向公众 / 原型）
- 涉及的敏感数据：[SENSITIVE_DATA]（或"无"）
- 非目标：[NON_GOALS]

你的任务不是重写这个项目。先理解代码实际做了什么，再从以下几个方面评估：功能完整性、轻量化资源使用、内存与并发安全、网络与服务端安全、隐私与数据泄漏风险、数据可靠性。

所有结论必须基于实际代码，不要给通用的最佳实践建议。请自己阅读代码——不要相信关于代码做了什么的描述。

项目根目录（请自行阅读代码）：[PROJECT_ROOT_ABS_PATH]
项目基线：[PROJECT_ANCHOR_ABS_PATH]
构建记录：[BUILD_NOTES_ABS_PATH]

## 1. 功能完整性
通读整个项目，总结：
- 目前真正实现并能跑通的功能有哪些
- 哪些功能只有 UI/接口存在，但实际上没有完整实现
- 系统当前实际读写的是什么数据/状态
- 文档或注释里提到的"同步""导入""断点续传""重试""去重""清理"等能力，是完整实现、部分实现，还是根本没实现
- 如果项目声称能处理进程重启/崩溃/断网，重启后状态是否真的能恢复

最后给出一张表：
```text
Fully implemented
Partially implemented
Not implemented
```

## 2. 轻量化设计
检查这个项目相对于它的定位是否足够轻量（内存、存储、CPU、电量如果适用、网络）：
- 是否会把大量数据一次性读进内存，而不是分批/流式/分页处理
- 日志、临时文件、缓存或本地数据库是否会无限增长
- 是否存在高频 timer / 轮询循环，或后台任务被过于频繁地唤醒
- 是否可能重复读取/上传/写入同一份数据
- 网络请求是否能合理合并成 batch，而不是逐条发送

请估计以下场景下的资源表现：正常使用一周、连续运行数月、长时间断网/离线、首次对一个已有的大数据集执行同步。

## 3. 内存安全与并发
针对项目实际使用的语言/技术栈，检查相应的并发风险，例如：
- 闭包长期持有外部作用域引用形成的引用环
- 没有取消路径的无限制 goroutine / 线程 / async task
- 注册了但从未移除的监听器/订阅
- 从未清除的 timer/interval
- 打开但没有可靠关闭的 socket / 数据库连接 / 文件句柄
- 对共享可变状态的竞态条件，尤其是：
  ```text
  操作 A 开始
  操作 B 在 A 完成前开始
  两者读到同一个 cursor/anchor/offset
  -> 重复写入 / 更新丢失 / 状态损坏
  ```
- 同一个 sync/save/upload 流程是否可能被并发触发两次，触发后会发生什么

## 4. 网络与服务端安全
如果项目会发起或接收网络请求，检查：
- 是否强制 HTTPS，是否可能悄悄退化为 HTTP
- TLS 证书校验是否存在且没有在任何地方被绕过
- 密钥/token：存放位置，是否可能出现在日志、URL 或未加密的本地存储里
- 重定向处理：Authorization header 是否可能被带到另一个域名
- 是否设置了请求超时；response body 大小是否有上限（防止恶意/异常服务器返回超大数据）
- 重试策略：是否存在无限重试、重试风暴，是否应该用 exponential backoff
- 如果有服务端组件：鉴权强度（是否容易被暴力破解、有没有限流）、注入风险、未校验的输入、唯一性/幂等约束、请求体大小是否有上限（防止靠撑爆磁盘/内存做 DoS）、是否向客户端暴露了 debug/堆栈信息、CORS 配置是否过宽

请结合部署场景判断证书 pinning 等强化手段是否真的有必要，还是过度工程化。

对本节发现的每个问题标级：
```text
Critical
High
Medium
Low
```

## 5. 隐私与数据泄漏风险
根据项目背景里列出的敏感数据（如果有），检查是否可能通过以下渠道泄漏：console/debug 输出、崩溃日志、埋点/分析、URL/查询字符串、通知、本地明文文件、本地数据库、浏览器/App 本地存储、网络请求体/header、服务端日志、反向代理/访问日志。

明确指出目前哪些渠道确实可能暴露敏感数据，具体是哪些字段。如果项目本身没有敏感数据，说明这一点，本节可以简短带过。

请结合部署场景判断本地存储保护（系统级 keychain、加密数据库、文件权限等）哪些是这个项目规模下必须做的，哪些属于过度工程化。

## 6. 数据可靠性
仅当系统存在多步骤或有状态的操作（写入后确认、上传后标记完成、队列处理、同步 cursor/anchor）时才需要评估，否则写"N/A，没有多步骤数据操作"。检查：
- 上传成功但状态没有持久化（或反过来）
- 数据被重复处理、被永久跳过，或重试后顺序被打乱
- 服务端部分成功被客户端当作完全成功处理
- 清理/retention 逻辑是否可能删掉尚未成功同步的数据
- 当前设计能否做到 at-least-once delivery 加接收端幂等；如果不能，实际的投递语义是什么

## 7. 保留期/清理逻辑（如适用）
仅当项目声明了明确的数据保留期或缓存清理策略时评估，否则写"N/A"。检查声明的限制是否真的生效、按什么字段清理、未上传成功的数据是否也会被一并清理、清理是否会导致再也无法补传某些数据。

## 8. 最终输出格式

先给出总体评分：
```text
Functional completeness: x/10
Lightweight design: x/10
Memory & concurrency safety: x/10
Network & server security: x/10
Privacy & data-leak risk: x/10
Data reliability: x/10（如果第 6 节是 N/A 则写 N/A）
```

**OVERALL SCORE**（1-10）：按以下权重加权平均（某个维度是 N/A 时按比例分配给其余维度）：功能完整性 15%、轻量化设计 15%、内存与并发安全 20%、网络与服务端安全 20%、隐私与数据泄漏风险 20%、数据可靠性 10%。

然后依次给出：

### A. Current capabilities
代码现在真正能做什么。

### B. Critical problems
只列必须立即修复的问题。每条给出：文件、类/函数、问题、触发条件、后果、严重程度、具体的修改建议。

### C. Important improvements
影响稳定性、安全性或资源占用的问题，同样的详细程度。

### D. Minor improvements
可以以后再优化的问题。

### E. Resource analysis
内存/存储/CPU/电量（如适用）/网络，对应第 2 节的各个场景。

### F. Security & privacy analysis
攻击面与数据泄漏渠道，对应第 4-5 节。

### G. Data-loss scenarios
可能导致数据丢失或重复的具体场景（如不适用写 N/A）。

### H. Final verdict
明确回答：
1. 相对于它的定位，这个项目是否足够轻量？
2. 是否适合长期连续运行/在预期规模下运行（长期后台进程、承受真实负载的服务端等）？
3. 是否存在明显的内存/资源泄漏风险？
4. 结合项目涉及的敏感数据（如果有），是否存在明显的数据泄漏风险？
5. 如果暴露在真实网络环境下，是否存在明显的攻击面风险？
6. 是否可以安全地用于真实用户数据/真实使用场景？
7. 在正式使用前最应该修复的 3～5 个问题是什么？

**Verdict**：READY / REVISE / RETHINK
- READY：总分 ≥ 9，没有未解决的 Critical，且 Final Verdict 里的回答都是干净、正面的
- REVISE：方向没问题，但还没到 READY 的标准
- RETHINK：存在根本性的设计或安全问题，靠小修小补解决不了

不要因为某个问题"理论上可能没事"就放松判断——请结合真实运行中的语言生命周期、框架行为和网络条件来判断。优先发现真正可能造成以下后果的问题，而不是花大量篇幅讨论代码风格：内存/存储持续增长、耗电、重复或丢失数据、密钥/token 泄漏、敏感数据泄漏、MITM、DoS、服务端被滥用。
```
